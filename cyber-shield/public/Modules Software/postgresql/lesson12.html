How Prepared Statements Work

Parameterized queries separate SQL code from data, preventing injection attacks.

PostgreSQL Prepared Statement Flow
Step 1: Prepare Statement
PREPARE get_user (text, text) AS
SELECT * FROM users
WHERE username = $1
AND password = $2;

-- Query plan created, parameters ($1, $2) are placeholders
-- Data cannot change query structure
Step 2: Execute with Parameters
EXECUTE get_user('john.doe', 'hashed_password123');

EXECUTE get_user("admin'--", "");

-- Both execute safely!
-- The injection attempt is treated as data, not code
-- Query searches for literal: username = "admin'--"
Step 3: Clean Up
DEALLOCATE get_user;

-- Or use persistent prepared statements
-- in connection pool

-- Node.js PostgreSQL automatically handles
-- preparation and execution

Key Security Principle

Never trust user input. Parameterized queries enforce this by separating code (SQL structure) from data (user input). The database treats parameters as literal values, never executable code.

MSEBETSI Security Schema - PostgreSQL
-- SECURITY DATABASE SCHEMA FOR MSEBETSI CLIENTS
CREATE TABLE security_events (
  event_id SERIAL PRIMARY KEY,
  event_type VARCHAR(50) NOT NULL,
  severity VARCHAR(20) CHECK (severity IN ('LOW', 'MEDIUM', 'HIGH', 'CRITICAL')),
  source_ip INET,
  timestamp TIMESTAMPTZ DEFAULT NOW(),
  description TEXT,
  analyst_id INT REFERENCES security_analysts(id)
);

CREATE TABLE security_analysts (
  id SERIAL PRIMARY KEY,
  username VARCHAR(50) UNIQUE NOT NULL,
  email VARCHAR(100) UNIQUE NOT NULL,
  clearance_level INT DEFAULT 1
);

CREATE TABLE threat_indicators (
  indicator_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  indicator_type VARCHAR(50),
  value VARCHAR(500) NOT NULL,
  first_seen TIMESTAMPTZ,
  last_seen TIMESTAMPTZ,
  confidence_score DECIMAL(3,2)
);
